# Инструменты для модели: обращение к внутренним api.php

Заготовка для `llm-chat-app`. Файлы **не подключены** к работающему коду и
ничего в нём не меняют — это исходники и заплатки, которые вносятся в проект
вручную по гайду ниже. Сделано так намеренно: в проекте есть локальные правки,
и перезаписывать чужие файлы целиком нельзя.

## Идея в одном абзаце

Инструмент описывается **данными**, а не кодом: строка в таблице `dpis_tools`,
где лежат URL и текст «когда это применять». Из строки на лету строится
pydantic-модель, из неё — JSON-схема для модели. Та же pydantic-модель проверяет
аргументы, которые модель придумала, поэтому описание параметров живёт ровно в
одном месте и разъехаться с проверкой не может. Добавить ручку = добавить строку
через админ-панель: ни правки кода, ни переноса файлов на изолированную машину.

### Если чего-то всё же не хватит

Порядок тот же, что в `docs-offline-transfer-setup.txt`: качаем на машине A,
переносим, ставим на B. Все нужные здесь колёса — **чистый Python**
(`py3-none-any`), то есть от платформы и версии Python не зависят, и возня с
`--platform win_amd64` для них не нужна. Но флаги оставлены: если понадобится
что-то бинарное, они спасут от скачивания колеса не под ту платформу.

**Вариант 1 — pip download (предпочтительный, тянет зависимости сам):**

```bat
:: на машине A

    --only-binary=:all: --platform win_amd64 ^
    --python-version 311 --implementation cp --abi cp311 ^
    -c D:\transfer\constraints.txt
```

Флаг `-c constraints.txt` обязателен: без него pip заодно подтянет свежий
`pydantic` или `numpy` и сломает рабочее окружение. Файл снимается на машине B
командой `pip freeze > D:\transfer\constraints.txt`.

**Вариант 2 — curl напрямую,** когда pip недоступен или нужен ровно один файл:

Ссылки на любую другую версию берутся так (хэш в пути у каждой версии свой,

# Часть 2. Порядок работ

## Шаг 1. Проверить окружение — ДО всех правок

```bat
D:\bundle\ml-bundle\.venv\Scripts\activate
python check_env.py
```

Скрипт ничего не меняет. Проверяет три вещи по отдельности: пакеты на месте,
схема инструмента строится, LLM-сервер умеет вызывать функции.

Третья проверка — главная, и провалиться она может по-настоящему. Если ваш
`.gguf` или сборка `llama-cpp-python` не поддерживают функции, модель ответит
текстом вместо вызова, и **всё остальное не имеет смысла**, пока это не решено.
Пять минут здесь экономят день. На этом шаге `/chat_tools` ещё нет — так и
должно быть, скрипт скажет об этом внятно; вернитесь к нему после шага 4.

## Шаг 2. Миграция базы

```bat
D:\bundle\ml-bundle\.venv\Scripts\activate
cd llm-chat-app\backend
python ..\..\llm-tools\apply_tools_schema.py
```

Появятся `dpis_tools`, `dpis_tool_calls` и три строки в `dpis_settings`.
Существующие таблицы не трогаются, аналога `--drop` у скрипта нет намеренно.
Запускать можно повторно: `ORA-00955` («имя уже занято») помечается как
`[есть]`, а не как сбой.

Штатный `apply_schema.py` для этого не подходит — он жёстко читает `schema.sql`
и произвольный файл принять не умеет. А `sqlplus` брать не стоит: он не входит
в Instant Client Basic, и на машине B его может просто не быть. Поэтому
отдельный скрипт, работающий через тот же `oracledb`, что и приложение.

Проверить результат:

```sql
SELECT COUNT(*) FROM dpis_tools;   -- 0 строк, но таблица есть
```

**Про точку с запятой в комментариях.** Разбиение SQL на команды и в вашем
`apply_schema.py`, и здесь сделано простым `split(";")`. Поэтому `;` внутри
комментария `--` разрывает комментарий, и его хвост приклеивается к следующей
команде, ломая её (`ORA-00900`). При правке `.sql`-файлов из этой папки
точки с запятой в комментариях не ставьте.

## Шаг 3. Настройки backend'а

В `backend/app/config.py` дописать:

```python
# Внутренние api.php, к которым ходят инструменты модели
TOOLS_API_BASE = os.getenv("TOOLS_API_BASE", "http://intranet.example.local")
TOOLS_TIMEOUT = int(os.getenv("TOOLS_TIMEOUT", "20"))
TOOLS_API_TOKEN = os.getenv("TOOLS_API_TOKEN", "")  # см. заглушку авторизации
```

И те же три строки в `backend/.env` под ваш адрес.

## Шаг 4. Скопировать новые файлы

| Отсюда | Куда | Как |
|---|---|---|
| `tools_registry.py` | `backend/app/services/` | целиком, новый файл |
| `tools_executor.py` | `backend/app/services/` | целиком, новый файл |
| `tools_loop.py` | `backend/app/services/` | целиком, новый файл |
| `llm_server_addition.py` | `llm-server/server.py` | **дописать в конец** |
| `llm_client_addition.py` | `backend/app/services/llm_client.py` | **дописать в конец** |

Файлы с приставкой `_addition` — не модули. Если скопировать их целиком вместо
дописывания, не заработает ничего: они опираются на импорты и объекты, которые
уже есть в файлах-получателях.

После этого шага перезапустить `run_llm.bat` и снова прогнать `check_env.py` —
теперь третья проверка должна пройти.

## Шаг 5. Заплатки в существующий код

Каждый файл `patch_*.py` — инструкция, а не модуль. Внутри написано, куда
именно вставлять и чем это проверить.

| Заплатка | Файл-получатель | Обязательна |
|---|---|---|
| `patch_settings.py` | `backend/app/services/settings.py` | **да** |
| `patch_messages_api.py` | `backend/app/api/messages.py` | **да** |
| `patch_frontend.js` | `frontend/src/api.js`, `views/ChatView.vue` | нет |

Про `patch_settings.py` стоит знать заранее, потому что ошибка там незаметна:
`get_all()` перебирает `SPEC`, а не строки таблицы, поэтому ключ, вставленный
миграцией, но не объявленный в коде, **молча не читается**. SQL отработает без
ошибок, панель ничего не покажет, а настройка не будет работать.

Фронт править не обязательно: разбор событий в `api.js` сделан цепочкой
`if/else if`, незнакомые события просто игнорируются, ничего не падает. Но с
инструментами ответ приходит куском, а не дельтами по токену, и экран молчит
секунд тридцать — строка «обращаюсь к …» снимает этот вопрос.

## Шаг 6. Первая ручка

Взять из `seed_tools.sql` самую безобидную, только на чтение, и завести одну.
Не десять сразу: если модель начнёт путаться, с одной ручкой понятно, в чём
дело.

```sql
UPDATE dpis_settings SET sval = '1' WHERE skey = 'tools_enabled';
COMMIT;
```

Проверять по возрастанию: сначала что при `tools_enabled = 0` чат работает как
раньше, потом с одной ручкой, потом вопрос, для которого ручки нет — модель
должна ответить текстом, не выдумывая вызов.

# Часть 3. Что осталось заглушками

**Авторизация в api.php** — `_auth_headers()` в `tools_executor.py`. Чем закрыты
ваши ручки, я не знаю; в коде расписаны три обычных варианта. Существенное:
если в api.php есть разграничение прав, инструменты должны ходить **от имени
вошедшего пользователя**, а не под общим сервисным токеном. Иначе через чат
утечёт то, к чему у человека доступа нет, и выглядеть это будет как обычный
ответ ассистента.

**Подтверждение изменяющих вызовов** — ветка `is_mutating` в `tools_loop.py`.
Сейчас такой вызов пишется в журнал со статусом `pending` и **отклоняется**:
молча выполнить изменение хуже, чем не выполнить. Чтобы довести до конца, нужен
разрыв потока — внутри одного SSE-соединения дождаться нажатия кнопки нельзя.

**Админ-панель для реестра.** Строки заводятся SQL-ом. Панель — следующий шаг,
и ради неё всё и затевалось: смысл реестра-как-данных в том, чтобы ручку
добавлял человек через форму, без переноса кода на изолированную машину.

**Отбор инструментов под запрос.** Пока в промпт уходят все включённые ручки.
При 8192 контекста десяток ручек съедает пятую часть бюджета ещё до первого
слова пользователя. Когда ручек станет больше пятнадцати, понадобится сначала
отбирать релевантные — `faiss-cpu` и `sentence-transformers` в бандле есть.

# Часть 4. Что проверено, а что нет

Прогон на `qwen3:14b` против живого API (`api.desperatemeasure.tech`, 113
товаров, только чтение). Демо — в `AItest/llm-tools-demo/`.

**Проверено и работает:**

- правильный инструмент выбран **7 раз из 7**, включая случаи, где правильным
  было ничего не вызывать;
- цепочка `search_products` → `get_product` отработала сама: модель взяла `slug`
  из первого ответа и подставила во второй;
- выдуманная категория `sofas` отвергнута схемой и **до сети не дошла**; модель
  прочитала список допустимых значений в тексте ошибки и исправилась;
- битая строка реестра с невалидным JSON отбрасывается, остальные работают;
- подстановка path- и query-параметров, обрезка длинного ответа.

**Не проверено ничем:**

- подключение к потоку сообщений — это шаг 5, кода в рабочем проекте пока нет;
- поведение на A4000 с llama.cpp: замеры сняты на Apple Silicon через Ollama.
  Цифры токенов от железа не зависят и перенесутся как есть, **скорость — нет**;
- поддержка `tools` вашей сборкой `llama-cpp-python` — это шаг 1.

**Известные издержки:**

- 3 инструмента в промпте = **500 токенов** (6.1% контекста 8192), ~170 на ручку;
- шаг цикла — полная генерация под глобальным `Lock` в `llm-server`. Цепочка из
  трёх шагов заняла около тридцати секунд, и всё это время очередь стоит. Для
  тестового стенда нормально, для нескольких одновременно работающих людей —
  нет, там цикл придётся выносить в очередь;
- модель дописывает параметры, которых пользователь не просил (`has_ar: true`,
  `price_min: 0`). Безвредно, но проверять аргументы надо всегда.
