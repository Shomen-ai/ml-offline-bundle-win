## 1. Структура backend'а

Сейчас всё лежит плоско в `app/`: роутер, схемы, SQL и работа с внешним сервисом перемешаны в одном файле. Целевая раскладка:

```
backend/app/
  main.py              создание приложения, lifespan, монтирование dist
  config.py            параметры процесса из .env (Oracle, LDAP, LLM_URL)
  db.py                пул oracledb
  deps.py              зависимости FastAPI: current_user
  api/
    auth.py            /api/auth
    dialogs.py         /api/dialogs
    messages.py        /api/dialogs/{id}/messages, SSE
    admin.py           /api/admin/settings, /api/admin/models
  schemas/             pydantic-модели запросов и ответов
    auth.py  dialogs.py  messages.py  settings.py
  services/
    ldap_auth.py       переезжает из app/ без изменений
    llm_client.py      переезжает из app/, дополняется tokenize и load
    settings.py        чтение и запись настроек LLM, кэш в памяти
    context.py         сборка контекста: бюджет токенов, обрезка, сжатие
    thinking.py        разбор <think>-блоков в потоке дельт
```

Правила, которые закрепляем заодно:

- `@app.on_event("startup"/"shutdown")` заменяется на `lifespan` — старая форма помечена устаревшей.
- Ручки, ходящие в Oracle, объявляются обычным `def`, а не `async def`: `oracledb` в thick-режиме синхронный, и FastAPI сам уводит такие функции в threadpool. Единственное исключение — SSE-стрим сообщений, он асинхронный по природе и уже использует `anyio.to_thread`.
- Ответы описываются `response_model`, чтобы схема в `/docs` не расходилась с реальностью.

Поведение не меняется ни в одном месте: проверка — вход, список диалогов, отправка сообщения.

## 2. Настройки LLM и админ-панель

### Хранение

```sql
CREATE TABLE dpis_settings (
    skey  VARCHAR2(64) PRIMARY KEY,
    sval  CLOB
);
```

Значение хранится CLOB'ом, потому что системный промпт легко перерастает 4000 байт. Колонки названы `skey`/`sval`: `key` и `value` в Oracle зарезервированы в ряде контекстов, не будем нарываться.

Ключи и их природа:

| Ключ | Смысл | Применение |
|---|---|---|
| `model_name` | активная модель | **холодная** |
| `n_ctx` | размер контекста | **холодная** |
| `n_gpu_layers` | слоёв на GPU | **холодная** |
| `temperature` | температура | горячая |
| `max_tokens` | потолок длины ответа | горячая |
| `system_prompt` | системный промпт (задача 1) | горячая |
| `thinking_enabled` | режим размышления по умолчанию | горячая |
| `thinking_models` | список моделей, понимающих `/no_think` | горячая |

Холодные требуют перезагрузки модели в VRAM, горячие действуют со следующего запроса. Значения по умолчанию берутся из `.env`, если строки в таблице ещё нет, — так стенд поднимается на пустой базе.

### API

- `GET /api/admin/settings` → текущие значения плюс список холодных ключей, чтобы фронт не хардкодил его у себя.
- `PUT /api/admin/settings` → сохраняет, при изменении холодного ключа дёргает `POST /load` на LLM-сервере и возвращает `{"reloaded": true}`.
- `GET /api/admin/models` → список `.gguf` из `MODELS_DIR` (сейчас это `/api/models`, переезжает в админский роутер).

LLM-серверу расширяется `LoadRequest`: `n_ctx` и `n_gpu_layers` становятся необязательными полями, сейчас они читаются только из переменных окружения при старте процесса.

Следствие для чата: модель становится глобальной настройкой, поэтому селектор модели из шапки диалога убирается. Колонка `dpis_dialogs.model_name` остаётся в таблице ради старых данных, но в сборке запроса больше не участвует — модель всегда берётся из настроек.

### Фронт

Новый маршрут `/admin`, `AdminView.vue`, ссылка в подвале боковой панели. По кнопке «Сохранить настройки» фронт пересекает изменённые поля со списком холодных ключей: если пересечение пустое — сохраняет молча, иначе показывает подтверждение с перечислением того, что перезагрузится, и предупреждением, что активные генерации оборвутся. Пока идёт перезагрузка — блокирующий индикатор, потому что первый ответ после неё всё равно будет ждать загрузку весов.

## 3. Контекст: подсчёт, обрезка, сжатие

### Подсчёт токенов

На LLM-сервере появляется `POST /tokenize` — принимает список строк, возвращает список длин в токенах. Ручка **не берёт generation-lock**: иначе она будет ждать окончания чужого ответа, и подсчёт станет бессмысленно медленным. Токенизация читает только словарь модели и не трогает состояние контекста; от одновременной подмены модели защищаемся отдельным лёгким мьютексом вокруг самого момента подмены.

Если ручка недоступна (старый LLM-сервер, модель не загружена) — падаем на грубую оценку по символам с запасом. Это страховка от полного отказа, а не рабочий режим.

### Бюджет

```
бюджет = n_ctx − max_tokens − токены(системный промпт) − накладные шаблона чата
```

Накладные — примерно 8 токенов на сообщение на маркеры ролей; берём с запасом. Сообщения набираются с конца, пока влезают. Системный промпт и сводка закрепляются: они не выбрасываются никогда.

### Сжатие

Перед каждым запросом считается, влезает ли история. Если нет:

1. Фронту уходит SSE-событие `status` с текстом «сжимаю историю» — иначе пауза выглядит зависанием.
2. Самая старая часть диалога, ещё не покрытая сводкой, уходит модели с промптом на сжатие — это отдельная генерация, и на однопоточном сервере она встаёт в общую очередь.
3. Результат пишется в `dpis_dialogs.summary`, отметка `summary_upto` хранит id последнего покрытого сообщения — чтобы не пересжимать одно и то же на каждом сообщении.
4. Контекст собирается заново: системный промпт → сводка отдельным `system`-сообщением → уместившийся хвост.

```sql
ALTER TABLE dpis_dialogs ADD (summary CLOB, summary_upto NUMBER);
```

Пользователь на таком сообщении ждёт две генерации подряд. Это принятая цена: альтернатива — молча терять начало диалога.

**Если не влезает даже одно последнее сообщение пользователя** — оно отвергается с внятным текстом («сообщение длиннее контекста модели») **до** записи в базу, чтобы в истории не оставалось висяков.

## 4. Режим размышления

На машине B стоят две Qwen3 разного размера и Qwen3.5. У Qwen3 `/no_think` — документированный мягкий переключатель, поведение Qwen3.5 не проверено, поэтому поддержка задаётся списком `thinking_models` в настройках, а не хардкодом. Модель не из списка — тумблер в интерфейсе не показывается, `/no_think` в промпт не подмешивается.

Когда режим выключен, `/no_think` дописывается к последнему сообщению пользователя (так этот переключатель и работает у Qwen3) — в базу этот суффикс не попадает, он живёт только в отправляемом контексте.

Поток дельт разбирается в `services/thinking.py`: содержимое между `<think>` и `</think>` уходит SSE-событием `think`, остальное — как сейчас событием `delta`. Разборщик обязан переживать разрыв тега между дельтами (`<th` + `ink>`), поэтому это маленький автомат с буфером, а не поиск подстроки.

**В базу размышления не пишутся вообще** — ни отдельной колонкой, ни внутри `content`. На экране они живут до перезагрузки страницы, в отдельном сворачиваемом блоке над ответом. Так они не жгут контекст следующего запроса, чего и рекомендует избегать сама Qwen3.

## 5. Что уже сделано (задача 2)

Пропажа сообщений имела две независимые причины:

- при ошибке генерации `chat.py` отдавал `event: error` и выходил **до** сохранения ответа, так что уже показанный кусок исчезал при следующем открытии диалога. Теперь частичный ответ сохраняется перед отдачей ошибки;
- во фронте временные ключи были константами `tmp-u` / `tmp-a` и не заменялись настоящими id, поэтому со второго сообщения в диалоге в `v-for` появлялись дубликаты и Vue переиспользовал чужие DOM-узлы. Теперь ключи уникальны и подменяются id из событий `start` и `done`.

## Тестирование

Ни Oracle, ни GPU на машине разработки нет, поэтому тестами покрываются чистые функции, которым ни то, ни другое не нужно:

- сборка контекста с подставным токенизатором: влезает / не влезает / не влезает даже последнее сообщение / сводка закреплена;
- разборщик `<think>`: тег целиком в одной дельте, тег разорван между дельтами, блока нет вовсе, блок не закрыт до конца потока;
- разделение настроек на горячие и холодные.

`pytest` в офлайн-бандл не входит и на машину B не переносится — тесты гоняются только на машине с интернетом.

Остальное проверяется руками на машине B: вход, отправка сообщения, переполнение длинного диалога, сохранение настроек с перезагрузкой модели и без.

## Риски

- **Qwen3.5 может не понимать `/no_think`.** Закрыто списком моделей в настройках, но проверить на живой машине придётся.
- **Сжатие удваивает ожидание** на однопоточном сервере. Смягчается статусом в интерфейсе; радикально — вторым инстансом llama.cpp, это за рамками задач.
- **Админка открыта всем авторизованным.** Осознанное решение для тестового стенда. Перед реальной эксплуатацией нужен либо флаг `is_admin`, либо роли — иначе любой пользователь перезагрузит модель под всеми.
- **Оценка накладных расходов шаблона чата приблизительна.** Если упрёмся в редкие переполнения — считать шаблон целиком, а не по сообщениям.
